# Lv.8 Coordinator Pattern

## 概念

**Coordinator** は、LLM エージェントがユーザーの意図を解釈し、
最適な専門エージェントに**動的にルーティング**するパターン。
事前にルールを全列挙する必要がなく、自然言語の理解力でルーティングを行う。

```
User Input
    │
    ▼
┌───────────────────────────┐
│   Coordinator (LLM)       │
│   意図を解釈 → 委譲先決定 │
└─────┬─────┬─────┬─────┬───┘
      │     │     │     │
      ▼     ▼     ▼     ▼
   [注文] [返品] [返金] [商品]
   Agent  Agent  Agent  Agent
   各 Agent が専用ツールで処理
```

## いつ使うか

✅ **適している場合:**
- ユーザーの意図が多岐にわたり、事前にルールを網羅しきれない
- 各専門領域が独立しており、専用のツールセットを持つ
- 自然言語でのルーティングが最も効率的な場合
- カスタマーサポート、ヘルプデスク、マルチドメイン FAQ

❌ **限界:**
- Coordinator 自体が LLM のため、ルーティングにもコストが発生
- ルーティング精度は description の品質に大きく依存する
- 確定的なルーティングが必要な場合は不向き（→ ルールベースを検討）

## Sequential (Lv.3) との違い

| 観点 | Sequential (Lv.3) | Coordinator (Lv.8) |
|---|---|---|
| ルーティング | 固定順序で全員が実行 | LLM が動的に 1 つ選択 |
| 柔軟性 | 🔴 低（順番固定） | 🟢 高（意図ベース） |
| コスト | 🟢 低（ルーティング不要） | 🟡 中（Coordinator も LLM） |
| 予測可能性 | 🟢 高（常に同じ順序） | 🟡 中（入力に依存） |
| 未知の入力への対応 | 🔴 弱い | 🟢 強い |

## このデモのユースケース

**カスタマーサポート自動化**

EC サイトのカスタマーサポートを 4 つの専門エージェントで対応する。
Coordinator が問い合わせ内容を分析し、最適な専門エージェントに振り分ける。

## アーキテクチャ

```
User: "注文 ORD-001 の配送状況を教えてください"
    │
    ▼
┌────────────────────────────────────────────────────┐
│  LlmAgent: customer_service_coordinator            │
│                                                    │
│  sub_agents の description を読んで委譲先を判断    │
│  ※ 自分では問題を解決せず、専門家に委譲           │
├────────────────────────────────────────────────────┤
│                                                    │
│  ┌─────────────────┐  ┌─────────────────┐          │
│  │ order_specialist │  │return_specialist │          │
│  │ 🔧 check_order  │  │ 🔧 process      │          │
│  │    _status       │  │    _return       │          │
│  │                  │  │    _request      │          │
│  └─────────────────┘  └─────────────────┘          │
│                                                    │
│  ┌─────────────────┐  ┌─────────────────┐          │
│  │refund_specialist │  │product_specialist│          │
│  │ 🔧 process      │  │ 🔧 get_product  │          │
│  │    _refund       │  │    _info         │          │
│  └─────────────────┘  └─────────────────┘          │
└────────────────────────────────────────────────────┘
```

## 重要: description の書き方

Coordinator パターンでは、`sub_agents` の **`description`** がルーティングの鍵。
Coordinator の LLM がこの説明を読んで「どのエージェントに委譲すべきか」を判断する。

```python
# ✅ 良い description: 具体的で判断しやすい
specialist_agent = LlmAgent(
    name="order_specialist",
    description="注文状況の確認、配送追跡に特化したエージェント。"
                "注文番号に関する問い合わせはすべてここへ。",
)

# ❌ 悪い description: 曖昧で判断できない
specialist_agent = LlmAgent(
    name="order_specialist",
    description="注文に関するエージェント",
)
```

## トレードオフ

| 観点 | 評価 |
|---|---|
| コスト | 🟡 中（Coordinator + 専門エージェント 1 つ以上の LLM 呼び出し） |
| レイテンシ | 🟡 中（ルーティング判断 + 実処理の 2 ステップ） |
| 複雑性 | 🟡 中（description の設計が重要） |
| 柔軟性 | 🟢 高（新しい専門エージェントの追加が容易） |
| スケーラビリティ | 🟢 高（sub_agents を増やすだけで拡張可能） |
| 予測可能性 | 🟡 中（LLM のルーティング判断に依存） |

## 学習ポイント

1. **`sub_agents` による動的委譲** — Coordinator の LLM が `sub_agents` の `description` を読んで最適なエージェントを選択する仕組み
2. **`description` がルーティングの精度を決定する** — 具体的で判断しやすい description を書くことが Coordinator パターンの成功の鍵
3. **各専門エージェントの独立性** — 各エージェントが独自のツールセット（`check_order_status` 等）を持ち、関心の分離を実現
4. **Coordinator の instruction 設計** — 「自分では解決しない、必ず委譲する」というルールで役割を明確化
5. **LLM ルーティング vs ルールベース** — 柔軟性が高い反面、確定的なルーティングが必要なケースではルールベースを検討すべき
